# Развёртывание на REG.RU — после покупки домена и хостинга

Сейчас выполнена локальная подготовка. Эта инструкция не означает, что сервер уже настроен. Доступы, IP, домен и пароль SMTP на данном этапе не требуются. Не менять действующую публикацию GitHub Pages; не загружать туда PHP или секреты.

## 1. Выбор тарифа и вопросы поддержке

Нужен Linux-хостинг с исполнением PHP, а не только статических файлов. Конкретный тариф подтвердить до покупки. Согласно [инструкции REG.RU](https://help.reg.ru/support/hosting/php-asp-net-i-skripty/kak-izmenit-parametry-php), PHP поддерживается на Linux-тарифах, кроме Host-Lite; состав тарифов следует перепроверить при заказе.

Требования этого обработчика:

- Актуальная поддерживаемая ветка PHP **8.4 или новее**, свежий security patch; [сроки поддержки PHP](https://www.php.net/supported-versions.php). Старую ветку с заканчивающейся поддержкой не выбирать для нового размещения.
- Расширения `openssl`, `mbstring`, `PDO`, `pdo_sqlite`; стандартные `ctype`, `filter`, `hash`, `json`. SQLite на локальном диске с корректными блокировками, доступном всем PHP-процессам. Несколько серверов или NFS без надёжных блокировок требуют общего Redis/БД-лимитера вместо этого SQLite-варианта.
- Приватный каталог вне **всех** document root учётной записи, доступный PHP с учётом `open_basedir`; права на создание SQLite и журналов транзакций. Сам каталог не должен быть HTTP-алиасом/симлинком из публичного дерева.
- Исходящий SMTP через TLS, нужный порт 465 либо 587, разрешённые провайдером лимиты/политика; актуальное хранилище доверенных CA.
- Возможность задать PHP environment `ELENA_CONTACT_PRIVATE_DIR` или изменить абсолютный путь в публичном входе (путь не является паролем).
- Исполнение `.php` именно как PHP. Узнать веб-сервер: Apache 2.4 с `mod_headers`, `mod_rewrite`, `AllowOverride` для нужных директив или nginx/другая схема. `.htaccess` относится к Apache: [REG.RU](https://help.reg.ru/support/hosting/fayly-web-config-i-htaccess/kak-sozdat-fayl-htaccess).
- SSL-сертификат с автоматическим продлением, резервные копии, возможность отключить запись тел заявок и SMTP debug. Узнать, как PHP получает реальный клиентский IP и признак HTTPS за прокси.
- SSH/Composer удобны, но необязательны: зависимости можно установить локально под совместимую PHP-платформу и передать SFTP.

Не предполагаем названий каталогов и логина хостинга. Плейсхолдеры ниже **не являются реальными путями REG.RU** — заменить по данным панели/поддержки.

## 2. Структура размещения

```text
<DOCUMENT_ROOT>/              ← содержимое финального dist, не весь проект
  index.html, 404.html, thanks.html, assets/, fonts/, ...
  api/contact.php             ← только security/php/contact.php
  .htaccess                   ← только после проверки Apache и генерации CSP

<PRIVATE_CONTACT_DIR>/        ← вне document root, вне HTTP-алиасов
  App.php                     ← security/php/App.php
  config.php                  ← копия smtp.example.php, значения задаются на сервере
  vendor/                     ← приватные Composer-зависимости
  runtime/                    ← 0700, SQLite создаётся обработчиком
```

Никогда не копировать на сайт `security/`, `src/`, `.git`, `.env`, `node_modules`, `qa`, Composer/npm-файлы, архивы или бэкапы. Документация и тесты остаются локально. Выбрать владельца PHP-процесса, затем минимальные права: приватные каталоги 0700, конфигурация/файлы 0600 либо эквивалент с минимальной группой при разделённых пользователях. Не применять 0777. Хранить исполняемый PHP и vendor доступными на чтение процессу, не публичному HTTP.

Если панель запрещает доступ PHP к приватной директории, остановиться и согласовать разрешённый путь/open_basedir с поддержкой. Для SMTP-секретов допустим закрытый environment/secret store провайдера, но bootstrap, vendor и SQLite всё равно требуют безопасного размещения. Если тариф этого не обеспечивает, выбрать другой тариф/VPS или отдельный приватный backend с same-origin reverse proxy. Не переносить `config.php` в document root, полагаясь только на расширение PHP или запрет `.htaccess`; эта реализация намеренно отвергает публичный приватный каталог. Альтернативная серверная схема потребует отдельной реализации/проверки.

## 3. Документы и сборка

С заказчиком утвердить содержание политики и согласия, оператора, правовое основание, размещение/локализацию, почтового обработчика и сроки хранения. Не публиковать выдуманные юридические тексты. Разместить утверждённые документы как публичные HTML/PDF, например в `public/legal/` перед сборкой. Убедиться в HTTP 200, правильном содержимом и доступности ссылок с телефона и клавиатуры.

В локальном окружении **только для будущей REG.RU-сборки** задать:

```dotenv
VITE_CONTACT_ENDPOINT=/api/contact.php
VITE_CONTACT_LEGAL_READY=true
VITE_PRIVACY_URL=/legal/REPLACE-WITH-APPROVED-PRIVACY.pdf
VITE_CONSENT_URL=/legal/REPLACE-WITH-APPROVED-CONSENT.pdf
SITE_URL=https://REPLACE-WITH-CANONICAL-DOMAIN/
VITE_METRIKA_ID=
```

Все эти значения публичные. Никаких SMTP-ключей в `VITE_*`. Для корневого размещения выполнить `npm ci`, `npm audit`, **`npm run build`** (base `/`), `node qa/seo-check.mjs`, `node security/scripts/check-public.mjs dist`. При размещении в подкаталоге отдельно согласовать base, endpoint, ссылки документов и ErrorDocument; текущий Apache-пример рассчитан на корень. Не переписывать base в workflow Pages: он остаётся `/----------/`.

Сборка автоматически останавливается, если найдены приватные пути, запрещённые расширения, карты исходников или известные шаблоны секретов. Это ограниченный pattern scan, а не доказательство отсутствия любого возможного секрета. Проверить список файлов вручную. Загружать SFTP только содержимое `dist`.

## 4. Установка PHP и SMTP

Выполнить `composer install --working-dir=security --no-dev --prefer-dist --no-plugins --no-scripts`, затем `composer audit --working-dir=security`. Зафиксирован PHPMailer в `composer.lock`; не обновлять на сервере бесконтрольно. `security/vendor` передать в `<PRIVATE_CONTACT_DIR>/vendor`. Проверить расширения и `composer check-platform-reqs --working-dir=security --no-dev` на целевом PHP. [PHPMailer](https://github.com/PHPMailer/PHPMailer) рекомендует Composer.

Скопировать `App.php` и `smtp.example.php` как приватный `config.php`, создать приватный `runtime`. Конфигурация по умолчанию выключена. На сервере вне Git заполнить:

- `origin`: точный канонический HTTPS origin без завершающего `/`, пути, query; IDN-домен в ASCII/punycode. Привести www/без www к одному адресу до включения формы.
- `rate_key`: отдельная случайная строка минимум 64 знака; сгенерировать серверным `bin2hex(random_bytes(32))`, не публиковать.
- `rate_db`: абсолютный приватный путь к SQLite либо `__DIR__.'/runtime/rate.sqlite'`; БД создаётся автоматически, каталог уже должен существовать.
- `smtp.host`, `port`, `encryption`, `username`, `password`, `from`, `to`: по выбранному почтовому сервису. Только SMTPS:465 или STARTTLS:587. `from` совпадает с авторизованным адресом `username`; если сервис использует иной тип логина, конфигурацию валидатора адаптировать после проверки сервиса, не подставлять адрес пользователя.
- `enabled` и `legal_ready`: true только после реальной настройки и согласования документов.

Пароль вводить через защищённую панель/редактор по SSH/SFTP без команд в истории и без пересылки в чат. Не хранить его в локальном рабочем дереве. Не включать SMTPDebug. Проверка сертификата и имени сервера включена; нельзя обходить её при ошибке — проверить hostname, часы, CA, порт и настройки провайдера.

В панели/PHP-FPM задать `ELENA_CONTACT_PRIVATE_DIR=<PRIVATE_CONTACT_DIR>`. Если environment недоступен, в **серверной копии** `contact.php` заменить пустую строку fallback для privatePath на абсолютный приватный путь. Конфигурацию со значениями не переносить в публичный файл. `display_errors=Off` на уровне хостинга обязателен: PHP startup/parse errors происходят ещё до `ini_set` в скрипте.

Для REG.RU или другого SMTP-сервиса брать фактический host/порты из панели: [инструкция REG.RU по почте](https://help.reg.ru/support/hosting/nastroyka-pochty-regru/nastroyka-pochty-i-pochtovykh-kliyentovv/nastroyka-pochtovykh-kliyentovv). Не считать SMTP-адрес выбранным заранее.

## 5. HTTPS, заголовки и защита файлов

Подключить сертификат, проверить цепочку и продление. Если Apache действительно поддерживает шаблон, выполнить **после финальной сборки**:

```sh
node security/scripts/prepare-apache.mjs dist
```

Получится `security/.generated/.htaccess`: CSP с хешами существующих inline-скриптов и JSON-LD, nosniff, Referrer-Policy, запрет встраивания, отключение листинга, запрет скрытых/служебных/резервных файлов. Inline styles пока разрешены для существующих style-атрибутов и анимаций; `unsafe-inline` для JS и `unsafe-eval` отсутствуют. Ресурсы сейчас локальные; аналитический скрипт не установлен. При добавлении Метрики/других ресурсов заново проверить CSP, согласие и передачу данных. Не добавлять широкие `*`.

В generated-файле после проверки прямого HTTPS/прокси раскомментировать HTTPS redirect и заменить `YOUR-CANONICAL-DOMAIN` фактическим фиксированным каноническим доменом. Не строить redirect из непроверенного Host. За прокси узнать поддерживаемый признак HTTPS; не доверять клиентскому `X-Forwarded-Proto`. Неправильное условие вызовет цикл. После проверки загрузить `.htaccess` отдельно в document root. После **каждой** пересборки заново генерировать хеши и обновлять заголовок атомарно вместе со сборкой.

На nginx-only сервере `.htaccess` не применяется. Передать провайдеру эквивалентные требования к server/location, HTTPS, заголовкам, закрытым путям и 404; не публиковать неподходящую конфигурацию. Apache-директивы/AllowOverride на REG.RU локально проверить нельзя.

HSTS изначально выключен. Включать только после стабильного HTTPS/продления, начать с короткого max-age, затем увеличивать. `includeSubDomains`/preload не включать без готовности всех поддоменов.

Проверить HTTP GET/HEAD снаружи (не по файловой системе): `/.env`, `/.env.example`, `/.git/config`, `/security/README.md`, `/src/js/form.js`, `/vendor/autoload.php`, `/config.php`, `/smtp.local.php`, `/package.json`, `/composer.lock`, `/backup.zip`, `/error.log`, `/rate.sqlite`. Допустимы 403/404; убедиться, что не выдаётся содержимое даже при HTTP 200 с кастомной 404. Проверить отсутствие directory listing и доступа к приватному каталогу через алиасы/другие сайты. `contact.php` должен возвращать JSON, никогда PHP-исходник. При любом раскрытии немедленно отключить обработчик, закрыть доступ и сменить затронутые секреты.

## 6. Приёмочные проверки формы и писем

Только после разрешения владельца тестового получателя отправить **одну синтетическую заявку**. До этого использовать локальные тесты. Проверить:

1. Пустая форма/нет согласия/некорректные значения не отправляются; имя, телефон и email обязательны. Политика и согласие доступны и содержат утверждённый текст.
2. POST JSON с валидными тестовыми данными → `{ok:true}` только после принятия SMTP; браузер переходит на thanks.html. По SMTP-логу провайдера и ящику получателя отдельно подтвердить появление письма, проверить «Спам»/отказы. Не утверждать, что HTTP 200 гарантирует конечную доставку.
3. Неверный метод → 405 с Allow: POST; тип → 415; большой запрос → 413; Origin → 403; JSON → 400; поля/honeypot → 422; лимиты → 429 с Retry-After; недоступная конфигурация/сервис → 503, явный отказ транспорта → 502. Исключения PHPMailer сейчас закрываются 503. Нет traceback/паролей/адресов во внешнем JSON.
4. Проверить единичные управляемые отказы SMTP и отсутствие ложного перехода; таймаут может быть неоднозначным, автоматически повторять нельзя. Нагрузочный тест публичного хостинга не проводить без отдельного разрешения.
5. Убедиться, что `REMOTE_ADDR` — реальный клиент, а не один адрес прокси. Не доверять произвольному X-Forwarded-For; настройка доверенных прокси нужна на уровне веб-сервера.
6. Проверить ограничения/права SQLite при одновременных запросах только на тестовом окружении. Текущие квоты консервативные; согласовать с владельцем ожидаемый трафик. Общая квота ограничивает ущерб, но ботнет может исчерпать её и мешать настоящим клиентам; для такого трафика потребуется дополнительная защита провайдера/проверенная CAPTCHA с отдельным анализом персональных данных.
7. Проверить HTTPS, CSP и визуальный вид на телефоне/планшете/компьютере. До исправления всех ошибок CSP не включать неподходящий заголовок на рабочем сайте.
8. В PHP/nginx/Apache/WAF/APM и почтовой диагностике отключить запись request body, SMTP transcript, полей формы и чувствительных заголовков. Стандартные access logs всё равно содержат IP/URL: согласовать доступ/срок хранения. Приложение заявки в лог не пишет. Запросы только POST, не query string.

## 7. DNS почты и резервные копии

По документации **фактически выбранного** почтового сервиса задать SPF для разрешённых отправителей (одна SPF-запись), включить DKIM, проверить выравнивание доменов From/SPF/DKIM. DMARC сначала наблюдение с согласованным адресом отчётов, затем quarantine/reject после проверки легитимной почты. Не выдумывать include, selector или публичный ключ. Для REG.RU руководствоваться [разделом почты](https://help.reg.ru/support/hosting/nastroyka-pochty-regru). Проверить Authentication-Results в доставленном тестовом письме.

Бэкапы кода и настроек хранить вне document root, с шифрованием и ограниченным доступом. Не создавать zip/sql/bak рядом с сайтом. Секретную конфигурацию включать только в защищённый backup с отдельным управлением ключами; SQLite-квоты и тестовые `.runtime` не архивировать. Почтовые ящики содержат заявки: отдельные права/2FA, согласованные сроки удаления и правила резервирования. Протестировать восстановление на изолированном стенде без автоматической отправки писем.

## 8. Что предоставит/утвердит заказчик позже

- Тариф, панель, web server/модули, PHP/расширения, document root и разрешённый приватный путь, схема HTTPS/прокси.
- Домен/канонический адрес, SSL, SMTP-сервис/порт/TLS, авторизованный отправитель и разрешённый тестовый/рабочий получатель. Пароль задаётся только на сервере.
- Оператор данных, юридические документы/основание, локализация и обработчики, сроки хранения почты/логов/backup, доступ сотрудников, ожидаемый трафик.
- Решение об аналитике и механизме согласия, если она нужна. Сейчас внешний счётчик автоматически не загружается, значения формы в цели не передаются.

Всё перечисленное требует подтверждения реального хостинга. Полное юридическое соответствие и безопасность целевой конфигурации до этих проверок не заявляются.
